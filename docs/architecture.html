planboard · how it is put together

planboard architecture

One local daemon connects three things: your browser showing the board, the plan file with its sidecar of notes and history, and whichever agent session is polling. This page walks through how the agent works with the plan, how polling works, where model and effort are decided, how a change travels from a saved file to a flashing item on your screen and how you review it, and how screenshots and whiteboard sketches reach the agent.

0The picture

Three parties, one daemon, one file

Nothing here is a cloud service or a model call. The daemon is a small Node process on your machine. The browser talks only to the daemon. The agent talks to the daemon through the CLI and edits the plan file directly. The daemon watches that file and keeps the board honest.

1Agent and plan

The agent edits Markdown, never HTML

The plan is an ordinary Markdown file with three conventions. The agent reads it with planboard show, edits it with its normal file tools, flips statuses with planboard set, and never generates any page markup. Because the renderer is fixed, every plan looks the same every day, and a diff of PLAN.md is a diff of the plan.

What the agent does, in order

  1. Orient. planboard show PLAN.md prints the plan as the board sees it: ids, statuses, how many notes sit on each item, and whether notes are pending. planboard thread PLAN.md site-soil prints one conversation.
  2. Open. planboard PLAN.md registers the board with the daemon (starting it if needed) and prints the URL plus the next step. Re-running is harmless.
  3. Wait. planboard poll PLAN.md --owner "Review agent" blocks until you press Send. Section 2 is about this call.
  4. Act on each note. Edit the file where the plan should change; planboard set PLAN.md <id> done to flip a status without touching the line by hand; planboard reply PLAN.md --to n_ywy527 "…" so the answer appears in that item's thread, not in chat.
  5. Poll again. The guidance forbids narrating the same answers in chat: the board is the conversation.

All of this is spelled out once, in planboard --help. The Claude Code, Cursor, and Codex integrations point there for the command contract, with polling guidance adapted to each host.

2Polling

One long request, answered when you press Send

The agent does not check the board on a timer. It issues one HTTP request that the daemon holds open. Your Send is what completes it. The response carries every sent note, the current text and status of the item each note points at, and the whole thread on that item so far, so the agent has the chain of thought without rereading anything.

Rules the poll obeys

  • At least once. Notes are marked delivered only after the response has been written to the socket. A poll that is killed mid-flight leaves them sent, so re-running the same command is always safe.
  • One listener per board. A second poll is refused with LISTENER_ACTIVE (exit 3). Pass --takeover to replace the current one; the old poll returns replaced.
  • Timeouts. Without --timeout the request waits until notes arrive. Claude Code supports tracked background commands, with --timeout 540 as a foreground fallback. Codex uses --timeout 30, collects any yielded shell session until it exits, and re-polls on {"status":"waiting"} during an active review. A skill does not guarantee a wakeup after the Codex turn ends. Cursor can use a bounded poll that fits its command timeout.
  • Queue first, send once. Notes wait as queued until you press Send, so you can walk the whole plan and deliver one coherent batch instead of waking the agent per click.

3Model and effort

The session that polls is the brain

planboard never calls a model. It only carries your notes to whichever agent session runs planboard poll, and carries that session's replies back. So the model and the effort level that process a note are properties of that session, not of planboard.

Today Set it in the session

In Claude Code, /model and /effort change the model and the reasoning effort for the next turn onward. The next batch of notes that session handles is processed with those settings. In Cursor and Codex, use the session’s model and reasoning settings. The owner label reports those settings; it does not change them.

Today See who is listening

The agent passes --owner "Review agent" when it polls, and the board shows that label next to agent is listening. The label is supplied by the caller, not a verified model identity; if it says no agent listening, nothing will read your notes until a poll starts.

Today Two sessions, one board

Only one poll may listen at a time. To hand a board to a different model, start the poll from that session with --takeover; the first session's poll returns replaced and stops. Your notes are never lost in the hand-over, because they stay sent until a response is written.

Today Per note: depth

The composer has a quick · normal · deep switch. The choice travels with the note as "depth" in the poll JSON, and next_step adds one line of guidance when a batch contains quick or deep notes. quick = a one-line answer from what the agent knows, trivial edits only; normal = read, change, verify, reply briefly; deep = research, weigh alternatives, implement and verify, explain the reasoning in the reply. Depth says how hard to work on that note; the model stays the session's.

How to think about it: /model and /effort pick the brain for the whole sitting; the depth switch says how much of it one note deserves. Both are visible: the owner label in the top bar, and a small quick / deep tag on the note bubble.
4Flow of changes

From a saved file to a flashing item

Every change to the plan, whether the agent wrote it, you flipped a status from the panel, or you edited the file in an editor, takes the same path. The daemon does not trust anyone to declare what changed; it derives the change by comparing the new parse with the last one.

What "changed since your last visit" means

The browser heartbeats while the tab is visible. A gap of more than 30 minutes ends a visit. When you come back, everything logged after the previous visit ended is tagged on the items themselves (To do → Done · 2 h ago), counted in the amber chip in the top bar, and grouped in the Changes tab. On the very first visit, and during the current one, the basis is the moment you opened the board, so work the agent does while you watch is tagged too.

Because the history is derived, nothing depends on the agent being disciplined about announcing edits. A rewording of an item with a stable id shows as reworded; an item whose id changed shows as removed plus added, which is why planboard lint nags about missing ids.

Reviewing the changes: drawn, not listed

The Changes tab turns the same event list into pictures, all computed in the browser from events_since. The key trick is rebuilding each item's status at your last visit from the events after it: the first event of an item tells its old status (the from of a status flip; "not there yet" for an added item), a removed event tells that it is gone now, and an item with no events did not move. With then-and-now known for every item, the rest is arithmetic.

Working the board

Three filters (Open, Changed, With notes) combine and hide everything else, dimming sections left empty. Sections that are 100 % done fold to their heading, unfold with a chevron or Expand done, and unfold by themselves when you select something inside. The keyboard covers the review: j/k move, Enter opens the thread, Esc goes back, o/c/t toggle filters, 1/2/3 switch tabs, ? lists them. Under 900 px the panel becomes a bottom sheet with a handle.

5Anchors and notes

What a click becomes

A note is text plus an anchor. The anchor is what you clicked, reduced to a fixed shape the daemon validates before storing. Threads are grouped by anchor, so all notes about one item, from either side, sit together.

6Screenshots and the whiteboard

Pictures travel as files beside the plan

Two kinds of pictures reach the agent. A screenshot you paste, drop or pick with 📎 is uploaded as raw bytes, stored under PLAN.board/attachments/ with a fresh name, and referenced from the note by file name; the thread shows it, the poll hands the agent the absolute path, and the guidance tells it to look before answering. A whiteboard sketch is the same thing produced by an editor.

The whiteboard is lavish-axi's frame, spoken to over postMessage

Every Mermaid diagram has a ✎ Whiteboard button. It opens an overlay with an iframe that loads lavish-axi's prebuilt Excalidraw frame (copied at build time from the lavish-axi package into dist/whiteboard/, ~8 MB, served at /whiteboard-assets/). The frame converts the Mermaid source to an editable scene, autosaves while you draw, and on Queue feedback hands back a PNG and a list of what you added, removed, moved or relabeled. planboard turns that into a queued note on the diagram - the summary as text, the PNG and the .excalidraw scene as attachments - which you send like any other. The agent reads the list, looks at the picture, and rewrites the Mermaid.

The frame is loaded same-origin, without a sandbox, because the Mermaid it converts comes from your own plan file - the same trust the board already extends to the plan's HTML. A missing bundle simply removes the button.

The sidecar can be versioned with the plan to retain project discussion and status history. Machine-local visit timestamps and autosaved working scenes are excluded by its .gitignore. PLANBOARD_STATE_DIR can keep sidecars under a separate root, keyed by a hash of each plan path. The shipped example has an empty conversation and history.

Export for project records

planboard export PLAN.md --out notes/plan-with-threads.md (or the Export button in the top bar) writes one Markdown file: the plan as it is, with every thread folded in as a blockquote right under the item, heading, diagram or image it was about - who said what, when, at which depth, with attachments linked relative to the plan - then notes on the whole plan, threads on elements that no longer exist, and the status history by day. It reads without planboard, and it still parses as the same plan.

8Trust boundary

What the daemon believes, and whom

A note is an instruction your agent will act on, and the asset route serves files. That makes the daemon a target worth guarding even on one machine.

  • Loopback by default. The daemon binds 127.0.0.1. PLANBOARD_HOST=0.0.0.0 is what the sandbox needs so your Mac can reach 192.168.65.3:4747; the CLI prints a warning whenever it binds beyond loopback.
  • Host allowlist. Requests whose Host is not loopback, a bound address, or a local interface address are refused with 403. This is the defence against DNS rebinding, where a web page you visit resolves its own domain to 127.0.0.1 and talks to the daemon as if it were you.
  • Origin guard. Any state-changing request that carries a foreign Origin is refused; the CLI's header-less requests still pass.
  • Asset confinement. Images are served only from the plan's directory, checked both lexically and after resolving symlinks, so a link placed beside the plan cannot expose a file elsewhere.
  • Anchors are validated, the plan's own HTML is not. Raw HTML in PLAN.md renders as written, because the file is yours and your agent's. A plan copied from a stranger could carry script.
9Setting up an agent

One command contract, host-specific polling

Claude Code

planboard setup claude --global writes ~/.claude/skills/planboard/SKILL.md, a stub that appears as /planboard and points at planboard --help. Add --hook for a SessionStart hook that lists open boards and pending notes at the start of every session.

Cursor

Inside a project, planboard setup cursor writes .cursor/skills/planboard/SKILL.md and a project rule .cursor/rules/planboard.mdc that Cursor applies when the conversation is about the plan. --agents-md appends a short section to AGENTS.md.

Codex

planboard setup codex writes .agents/skills/planboard/SKILL.md; --global uses ~/.agents/skills/planboard/SKILL.md. Invoke $planboard in the CLI or IDE, or select the skill in the app. The skill opens the board, uses bounded polls, edits the plan, replies on the board, and continues the active review. It collects a yielded shell session before starting another poll and stops on an intended handoff or closed board.

These paths and the YAML name/description header follow the official skill conventions. Existing AGENTS.md project instructions and Codex configuration remain unchanged. If discovery does not refresh, restart Codex.

From the sandbox to the Mac

The VM is a separate machine on a private network. Start with PLANBOARD_HOST=0.0.0.0 planboard PLAN.md --no-open and open http://192.168.65.3:4747/ in Safari; the home page lists every board. Store the plan on a persistent volume if the VM is disposable.

On the Mac itself

npm install && npm run build && npm link in the repo puts planboard on your path; the browser opens by itself on loopback. One daemon serves every plan on the machine; planboard boards lists them.
